# Held-out context-generation diagnostic — 2026-09-13

## What ran

Six synthetic requests, each for a different person, were sent to the configured
Groq `qwen/qwen3.8-27b` model in three arms: `none`, `oracle` (human-labeled
relevant memories), and `retrieved_local` (the local MiniLM retriever's output
from the separate 18-case holdout). All 18 calls succeeded with the same
production prompt policy, production mode temperatures, and a 768-token output
cap. Arm order rotated by case. The baseline policy SHA-256 is
`7ac8d776c1ee0da6181de15b960760dc3b183663c347248e9650c70e0112384d`.

Results are in the ignored local file
`/private/tmp/promptengine-three-arm-heldout-768-escalated-20260913.jsonl`.
The runner preserves synthetic inputs, complete outputs, selected memory IDs,
latency, usage, and **blank** human-review fields. Never commit a result file
containing real user prompts. A previous 1,200-token-cap attempt had two
provider failures (one hard output-token-tier rejection, one read timeout);
its successes must not be mixed into this consistent-cap comparison.

**Fixture correction:** Inspection later found that this first run passed
synthetic memory IDs as `title` fields for saved prompts. That is not a real
user-provided title and likely contributed to the fabricated museum name.
This first run is retained as a bug-finding baseline, **not** a clean
production-shaped context-generation estimate. The runner now leaves title
blank unless the fixture supplies a real one and hashes the exact model
request to prevent resuming across fixture changes.

## What the outputs show

All 18 outputs passed the deliberately narrow deterministic checks, but that
is **not** a semantic-quality pass rate. Inspection of the raw rewrites found:

| Case | Observation |
|---|---|
| Nina, cold starts | Both context arms correctly brought in Go, Cloud Run, and Spanner; the no-memory arm stayed generic. |
| Elena, food-web class | Despite identical relevant memories, the oracle output almost echoed the input while the retrieved output incorporated English-language learners and a low-stakes check. This is stochastic utilization variance, not evidence one retriever is better. |
| Tariq, black holes | All three arms had empty memory IDs as intended; all rewrites stayed on topic, though they expanded the simple request differently. |
| Sofia, museum label | The no-memory arm invented three options, a 50–100-word range, and a call to action. Both context arms used the exhibition topic and bilingual requirement, but showed a quoted, apparently formal title. The erroneous synthetic `title` field confounds attribution of that title error. |
| Dev, warehouse check | Both context arms incorporated the seven-day window and recovery, but neither included the relevant PII check; the oracle also omitted the dbt/BigQuery context. |
| Amina, rental refresh | Both context arms used the no-drilling constraint. The local retriever also selected an irrelevant proposal-format memory, but the output did not adopt its budget/must-have instructions. |

These observations identify **policy over-specification** and **context
utilization** as live problems. They do not establish a population win rate,
and a single stochastic completion per arm cannot distinguish sampling noise
from a policy or retrieval effect. In four cases the oracle and local arms had
the same memory set; Tariq had no memory in either; only Amina exposed a
substantive extra retrieved item. This is particularly weak for measuring
retrieval-caused damage.

## Change made in response

The production prompt's few-shot “right” examples contradicted its source-
fidelity rule: they invented an academic recommendation-engine domain, a
recruiter audience, and a study-plan goal. Those examples were rewritten to
preserve the unknown details. The policy now explicitly rejects speculative
deliverables, unsupported counts/ranges, and turning a remembered topic into
a quoted formal title. The ChatGPT platform hint no longer encourages headers
for every request. This creates a **new policy version**; any retest on Sofia
is a development diagnostic, not an untouched holdout result.

That corrected-fixture Sofia diagnostic completed 3/3 provider calls under
the same model and 768-token cap. Its no-memory rewrite requested missing
exhibition details without inventing three options or a word count; both
context arms used the known topic and bilingual requirement without claiming
an exact exhibition title. The local-retrieval arm additionally used the
plain-language preference. Raw synthetic results are in
`/private/tmp/promptengine-three-arm-sofia-corrected-20260913.jsonl`.
The revised policy SHA-256 is
`53f27c243960fcaf9e71ab6c31d4c03f2cbe09dc1e7d69b5c3fad2bf08f7764a`.
This is promising regression evidence for **one inspected case**, not a
statistical improvement claim or a clean A/B experiment; both the policy and
fixture changed since the first six-case run.

Separately, passive vector memory is now written only after the authenticated
user applies the enhanced text. The server resolves the original/refined pair
from that user's own log, uses an idempotent point ID, and queries only points
marked `approved=true`. Generated-but-dismissed and legacy unapproved
vectors are excluded. This does not prove end-to-end Chrome behavior; it is
covered by API/in-memory vector and extension static tests only.
If configured Mongo storage is unavailable, acceptance fails closed for
durable memory: the applied text remains in the composer, but no persistent
vector is written without a durable approval record.
The prompt-log TTL can eventually delete that record while the Qdrant vector
remains; a separate minimal consent ledger or aligned vector retention is
still required for long-term auditability and revocation.

## What still blocks a credible quality claim

1. Run a fresh, untouched and larger multi-person corpus with manually
   adjudicated intent/constraint/context labels. Include multiple samples per
   arm or deterministic sampling where the provider supports it. Reusing these
   six cases to tune the prompt is useful for debugging, not for an unbiased
   release estimate.
2. Exercise the *production* Qdrant/API/browser retrieval and apply paths with
   isolated test identities. `retrieved_local` is not that path. The available
   Chrome instance opened a personal-profile picker, so no synthetic test was
   run in the user's live profile.
3. Have a blinded reviewer score intent fidelity, unsupported additions,
   missing relevant context, language, and downstream utility. The JSONL's
   blank review fields are deliberate; deterministic pass must not be used as
   a substitute.
4. Add a reason for negative feedback and a revocation/supersession rule for
   accepted memories. Applying a rewrite is consent to use it, not proof every
   added detail was good. Resolve the log-TTL/vector-lifetime mismatch with a
   minimal long-lived approval ledger and user-facing deletion control.
5. Keep builder-visible metadata for generation/approval/retrieval failures,
   while redacting prompt content and credentials from operational logs.
